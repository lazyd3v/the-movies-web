# Original threading: next-risk audit

Read-only disassembly of MoviesSE.exe (SHA256 `48f909d7f89051ff0d3277f7dc0aa7c65cd1c92015542fcbc3d5f86700b1566a`) and inspection of the translated runtime, 2026-11-07. These paths have **not** been reached in the current static browser run; its observed blocker remains graphics state queries. Addresses below are original virtual addresses, not replacement entry points.

## Concrete call paths

`CreateThread` IAT is `D16330`; five real call sites are `ACFA69`, `BED290`, `C1BB20`, `C947D4`, `C94AFD`. `C9AE7A` is only an import jump thunk. `_beginthreadex` is statically linked, not an imported API: the six-argument cdecl wrapper starts `ACFA09` and calls CreateThread with start `ACF974`, parameter a newly allocated 0x8C-byte CRT thread-data block. That block stores user routine at +0x4C and user parameter at +0x50. The wrapper preserves caller stack-size, creation flags and thread-ID output. `ACF974` initializes original CRT TLS, calls the user routine at `ACF9E0`, and passes its result through `ACF943` to `ExitThread` at `ACF96D`. Replacing only the user routine would skip real CRT initialization/cleanup.

## Required runtime separation before CreateThread

- Each host pthread needs its own CPU registers/FPU state, guest stack allocation, guest TIB/FS base, and lifetime record. Do **not** call runtime_init for each child: it reallocates shared g_mem and assigns the same `GUEST_STACK_TOP=00300000`, `GUEST_TIB=00010000`. Generated code explicitly reads/writes `c->fs_base`, including the original start routines. The main bootstrap's static CPU is not reusable by children.
- `g_trap_jmp` and `g_trap_msg` currently are process globals. A child must never longjmp through the main thread's jmp_buf. Make trap context thread-local with per-thread boundary/parent failure notification. Runtime's static temporary error strings, lazy import/trace flags and trace counters/buffer are additional races: initialize shared configuration before launching, use local error buffers, and synchronize or isolate tracing.
- `g_import_target` and the FPU rounding cache already are thread-local; startup LastError and thread-api TLS values/thread IDs also are thread-local. Preserve these. Existing TLS and critical sections have locks, but they alone do not allocate guest stacks/TIBs or implement thread creation/exit/join handles.
- Shared guest memory must remain shared. Function dispatch is already protected by the applied growing-table patch; do not assess the unpatched upstream table as the running build. Guest x86 LOCK/XCHG translations use the runtime guest lock. Nevertheless plain generated R32/W32 accesses are ordinary C accesses: unsynchronized original shared-state polling needs an explicit compiler/data-race audit, not an assumption that all x86 memory semantics follow from pthreads.
- `guest_alloc`'s global bump pointer is unsynchronized upstream. Determine remaining live uses; use a locked allocator for new thread resources. Existing backend heap allocations have their own ownership rules.
- Window queue and media COM deliberately enforce their initialization thread. Cross-thread UI calls require dispatch to the window owner; per-thread COM apartments require separate state. A generic CreateThread implementation cannot make those modules thread-safe. Registry/process shared mutable state and every JS bridge also need caller ownership review before permitting arbitrary worker API calls.
- Closing a thread handle must not terminate the running thread. Exiting must signal completion and preserve exit status; waiters and handles need independent references. Existing CloseHandle resolver and mutex-only wait dispatch require typed thread/event integration, including timeout and abandonment behavior. `ExitThread` must terminate only that guest thread and unwind its host boundary; it cannot call process-wide exit.

## Emscripten integration constraints

Compile **all** translated/runtime/API objects and final link with `-pthread`; a shared JS SAB used by the current service protocols alone does not turn Wasm guest memory into shared pthread memory. Prewarm a bounded `PTHREAD_POOL_SIZE` before original entry, and wait for readiness. Child creation followed immediately by a blocking wait must not depend on the blocked runtime worker returning to its event loop. A finite pool needs explicit exhaustion handling; do not manufacture thread handles when no worker can start. [Emscripten pthread guidance](https://emscripten.org/docs/porting/pthreads) and [compiler settings](https://emscripten.org/docs/tools_reference/settings_reference.html) explain the pool and main-thread blocking constraints.

The current guest main runs in a dedicated browser worker, not an Emscripten pthread. Two viable designs need an isolated proof before choosing: keep that worker as Emscripten runtime owner with an entirely prewarmed pool, or move guest main to a pthread while the runtime owner remains responsive. Neither is a flag-only change: existing Module media/GPU/window callbacks, page-owned MessagePorts and synchronous response SABs are JS realm-local. Pthread worker startup does not automatically copy callable closures or transfer ports. Explicitly initialize child bridge capabilities or route requests through a responsive owner; do not let a worker synchronously proxy to the same thread waiting for it. Preserve the already-fixed generated mainScriptUrlOrBlob worker entry and cross-origin isolation.

First acceptance should execute a real translated stdcall start with independent FS/TLS/stack, return an exit code, wait/close in both orders, exercise event shutdown and exhausted-pool failures, then run the actual first observed game thread. No gameplay-thread performance claim is established by this audit.

The actual browser run now stops at CreateEventA near `A56559`. Parent audit of `A56540` identifies three unnamed event configurations: auto-reset/nonsignaled, manual-reset/nonsignaled, manual-reset/signaled. The immediately following original `_beginthreadex` call at `A5658B` (return `A56590`) supplies user start `A55E90`, NULL parameter and flags0. This path precedes the earlier `543348` thread in current execution; it is the next original thread acceptance target. Guest threading remains disabled. The published event-only implementation supports these states, while a nonpthread Wasm unsignaled blocking wait explicitly returns WAIT_FAILED/ERROR_NOT_SUPPORTED; polling and already-signaled waits retain real event semantics.

## Implemented foundation and actual browser acceptance

The separate `--threads` profile foundation is now published; it does not enable threading in the regular profile. `scripts/test-guest-threads.py --browser` reproduces native sanitizer, Wasm and browser fixtures. Browser evidence is `docs/evidence/thread-browser-persistent.log`/`.jpg` and `thread-browser-serialized.log`/`.jpg`. The latter links the actual patched runtime with guest thread/TLS/sync APIs and proves independent guest CPU/FS/stack/TLS identities, event waits, genuine return/ExitThread completion, close-before-exit lifetime, pool exhaustion and isolated child traps. Start routines are synthetic ABI probes; **original ACF974/A55E90 execution remains to be verified**.

A persistent pool of two real host pthreads executes successive guest jobs. Detached Emscripten workers failed to recycle while the parent remained in synchronous guest execution: cleanup requires a JS message event, not just queued-C-call servicing. Persistent workers remove that dependency. Every guest job receives a new guest ID/stack/TIB and cleared TLS values, LastError, trace/import state; mutex ownership is abandoned on exit. Completion remains independently reference-counted from CloseHandle. Initial-thread ExitThread and nonzero creation flags remain explicit unsupported cases.

The thread safety patch applies **after** function-table and import-boundary patches and requires rebuilding all objects. With `MOVIES_GUEST_THREADS`, scalar memory accessors use the same reentrant lock as translated LOCK groups and native Interlocked APIs. It handles unaligned accesses without pretending they are naturally aligned Wasm atomics. Guest-facing bulk memcpy/memmove/memset are protected too; the generated-source audit found5401 memcpy and4098 memmove HP uses and no other raw HP operation families. Runtime trap exits release held guest locks before unwinding. Nonthreaded behavior does not enable this serialization. This is a correctness baseline with **unmeasured game performance**, not a performant-threading claim.

Observed locked families provide a bounded optimization opportunity:36 dword LOCK XADD,13 dword XCHG,23 byte XCHG,1 dword LOCK CMPXCHG,1 byte LOCK ADD and1 byte LOCK AND. A later translator specialization can use atomic fetch-add/exchange/CAS/fetch-and while preserving original register and flag results. It must retain a serialized fallback for unaligned/overlapping access and synchronize ordinary accesses consistently; replacing scalar loads with atomics alone does not make the existing separate LOCK read/write sequences atomic.

Native blocking file I/O deliberately does not hold the guest memory lock across a proxy wait. Its output buffers require the Windows caller ownership contract until return. Caller-provided strings/direct buffers in native APIs also must not be concurrently mutated. No proof extends to arbitrary raceful API arguments, cross-thread graphics/media/window calls or all original job destructors. The independently tested file-service queue pump must run on the runtime owner during long compute periods; child callbacks/MessagePorts are not automatically inherited. Original CPU raster work can lazily read geometry, so that bridge is required before claiming the first real job completes.
