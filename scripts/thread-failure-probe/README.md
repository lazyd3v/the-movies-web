# Shared fatal-thread watchdog

The actual native thread backend exposes an immutable first-failure record through `movies_guest_threads_failure_view`: aligned shared uint32 ready flag, NUL-terminated UTF-8 message, capacity 256. Publication writes the message then release-stores ready=1. The main runtime's `Module.moviesThreadFailureWatch` callback forwards the initial shared Wasm buffer and offsets to the page before entering guest execution; no child JavaScript provider is needed.

The page watchdog in `public/static-probe.js` validates the shared buffer, safe integer offsets, flag alignment, bounds and nonoverlap. It checks the flag every 100 ms and reacts only to a published failure. There is no timeout-based declaration that a slow game failed. After acquire-loading ready=1, it copies at most the declared message capacity to nonshared memory before TextDecoder, then routes through normal finish/cleanup. Existing views remain valid after shared Wasm memory growth because both globals reside inside the initial buffer. A stopped/stale run cannot publish a watcher into a new run; immediate failures during watcher creation are handled without retaining a stale watcher.

Tests: `node --test tests/thread-failure-watchdog.test.mjs tests/media-service.test.mjs`. They cover publication ordering, bounded UTF-8, malformed descriptors, stop/late notifications, memory growth, and launcher cleanup of audio/GPU/media services when a failure is already published.

Run `python3 scripts/thread-failure-probe/stage.py`, then open `/runtime/thread-failure-probe/` and click **Run failure lifecycle proof**. The fixture extracts the exact production watcher (hash in its manifest), starts a real nested browser worker, and blocks the parent in Atomics.wait. The child publishes a clearly labelled synthetic failure and increments a shared heartbeat. The page must report the message, terminate the parent, and observe that the child heartbeat stops. A separate five-second fixture supervision timeout is a failed test, never an inferred guest failure. The fixture does not run original game code or claim an actual original child has trapped. The original nested-worker browser run detected the failure but **failed cleanup**: child heartbeat advanced from 20 to 45 after parent termination. Parent Worker.terminate does not terminate its nested children in the tested browser. That result invalidates parent-only teardown.

The repaired fixture and threaded launcher use `public/owned-worker-host.js` on the page and `public/owned-worker-client.js` in the logical parent. The page directly owns the real pthread workers; a MessagePort-backed Worker facade forwards construction, messages, transfer lists, errors and termination. Page cleanup closes all owned workers before terminating the blocked parent. Late create messages are ignored after close and worker script URL is restricted to the selected generated runtime. The synthetic fixture uses the same transport with its explicit child script. Repaired real-browser acceptance passed: the logical parent was blocked, the synthetic failure was reported, and child heartbeat remained 19 → 19 after page-owned termination. Evidence: [`thread-browser-owned-stop.json`](../../docs/evidence/thread-browser-owned-stop.json) and [capture](../../docs/evidence/thread-browser-owned-stop.jpg). This validates the production cleanup transport with synthetic workers; no threaded original-game execution or gameplay is established.
